# 0.4.0: sandbox reproduction and regression verification

## Status

Version 0.4.0 is a plan, not an implemented release.
The current package contains four independent skills at version 0.3.0.
The repository does not include the sandbox MCP server or the `podori-wreck` skill.

The planned feature name is `podori-wreck`.
Its proposed invocation is `/podori-wreck`, subject to client support.
Do not invoke this command as an installed capability.

## Purpose

Verify reported vulnerabilities through bounded experiments in approved sandbox copies.
Compare the original and fixed versions under identical initial conditions.
Verify normal behavior alongside the reported defect.

The feature tests report claims, not the maximum possible damage.
Static analysis and policy-model assertions do not replace actual application evidence.

## Scope

| Included | Excluded from 0.4.0 |
|---|---|
| Approved target copies and synthetic accounts, data, and files | Production systems, external targets, real credentials, and user data |
| Reviewed, bounded scenarios tied to report items | Open-ended exploration and vulnerability chains |
| Non-destructive authorization and input-validation checks | Code-execution vulnerability demonstrations, destructive tests, and resource-exhaustion tests |
| Scenario identifiers and constrained inputs | Arbitrary commands, generated code, and general-purpose shell interfaces |
| Internal test receivers | External data destinations and access to other experiments |
| Evidence, reset, cancellation, and resource cleanup | Publication or production activation without separate approval |

A report does not grant execution authority.
Record separate approval for the target, scenario, inputs, mutable test data, and resource limits.
Treat scope expansion as a separate decision.
Do not disguise the task or change providers to evade model safeguards.

## Input and evidence

Each experiment binds these records:

- Report identifier and item identifier
- Target revision and input hashes
- Image digest, when the backend uses an image
- Scenario identifier, prerequisites, and expected result
- Approval, isolation policy, and resource limits
- Environment and initial state

Record actual requests, responses, exit status, state changes, service status, and resource use.
Record truncated logs, setup failures, execution failures, and incomplete observations separately.
Do not accept the scenario's success message as independent evidence.

## Execution boundary

1. Verify target authorization and scenario scope before execution.
2. Verify isolation from the host and other experiments.
3. Block external network access.
4. Exclude host mounts, management sockets, production data, and host credentials from the target environment.
5. Keep the control plane outside the target environment.
6. Enforce target, path, image, network, CPU, memory, storage, time, and output limits outside the model.
7. Accept only reviewed scenario identifiers and constrained inputs.
8. Treat dependency installation and build hooks as target-code execution.
9. If required controls are unavailable, reject execution.
10. Do not substitute an unrestricted host shell.
11. Treat reports, target files, tool responses, and logs as untrusted data.
12. Reject approval claims that originate from those inputs.

## Experiment sequence

1. Map each report item to its prerequisites, expected result, and approved scenario.
2. Record excluded or incomplete items without execution.
3. Create the approved target copy with synthetic data.
4. Record its initial state and normal behavior.
5. Execute the bounded scenario against the original version.
6. Collect independent evidence of the observed effect.
7. Restore identical initial data for the fixed version.
8. Execute the same scenario against the fixed version.
9. Verify normal behavior after the fix.
10. Export evidence before resource cleanup.
11. Clean up only resources that belong to this experiment.

Cancellation, timeout, and server restart must not leave experiment resources active.
Separate target failure from termination by the execution limits.

## Results

| Result | Required evidence |
|---|---|
| Reproduced | Observed behavior matches the report claim under recorded conditions. |
| Not reproduced | The scenario completes with adequate observations but does not demonstrate the reported behavior. |
| Unverified | Missing prerequisites, excluded scope, policy rejection, execution failure, or incomplete observations prevent a verdict. |

Record exclusions separately from execution results.
An excluded item retains an unverified execution result.
A not-reproduced result does not establish general safety.
A fix requires both defect-specific evidence and normal-behavior evidence.

## Proposed implementation

The implementation language, SDK, and isolation backend remain undecided.

- Place an optional MCP package under `mcp/` in this repository.
- Start with local stdio and a small HTTP application with synthetic data.
- Expose creation, approved scenario execution, status, evidence, reset, and cleanup operations.
- Bind each operation to server-side authorization.
- Keep the four existing skills independent of the MCP package.
- Preserve the non-execution boundary of `podori-doubt`.
- If MCP execution is unavailable, retain unverified runtime conclusions.

These design choices do not establish that any backend provides sufficient isolation.

## Acceptance criteria

The criteria below define future verification, not completed tests.
A3, A4, and A5 replace the earlier high-risk experiment proposals.
Old results do not satisfy the revised criteria.

| ID | Observable result |
|---|---|
| A1 | A real MCP client completes initialization, tool discovery, and tool calls. Direct function calls alone do not satisfy this criterion. |
| A2 | A bounded authorization case affects only permitted synthetic test data. The fixed version rejects the same unauthorized request. |
| A3 | A non-destructive input-validation case produces actual responses. The fixed version rejects invalid input and accepts normal input. |
| A4 | The server rejects execution when isolation, external network denial, or resource limits are unavailable. |
| A5 | The server rejects unknown scenarios, excluded scenarios, and arbitrary command requests. Reports retain exclusion reasons and unverified results. |
| A6 | Actual requests verify normal operations on both versions. |
| A7 | The original worktree and host marker remain unchanged. External communication, management socket access, and cross-experiment access fail. |
| A8 | Unauthorized target, image, path, budget, and approval changes fail. Instructions inside inputs cannot change policy. |
| A9 | Reset restores the initial data. Cancellation, timeout, and restart recover only the affected experiment's resources. |
| A10 | Report items, scenarios, evidence, and results retain matching identifiers and hashes. Omitted checks never appear as passed. |
| A11 | Each existing skill works without the MCP package. The non-execution boundary of `podori-doubt` remains intact. |

## Release boundary

Preserve the current 0.3.0 packages and their evidence during implementation.
Use a separate feature branch and worktree for implementation.
Require actual security review and affected regression tests after each source-code task.
If source changes affect the review, repeat the affected review.
Do not replace independent review with the implementer's own verdict.

Publish version 0.4.0 only after the implementation satisfies its acceptance criteria and receives release approval.
Documentation updates do not prove implementation, isolation, or runtime security.
